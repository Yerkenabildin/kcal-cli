# Private API risks

YAZIO publishes no API. Everything here talks to the private API behind the mobile app,
described by the community at
[`yazio-community/yazio-api-specification`](https://github.com/yazio-community/yazio-api-specification)
(API version 22). That description was **inferred from one account's captured traffic**: an
endpoint the app never exercised while recording is simply absent, and a field that happened to
be null throughout is typed from that null. It is a field guide, not a contract.

Consequences for this codebase: tolerate unknown fields, expect missing ones, and never treat
the absence of something from the spec as proof that the API lacks it.

## 1. `version_blocked` is the expected failure, not a hypothetical one

The API refuses any request whose client version it does not recognise, answering
`403 {"error":"version_blocked"}` on **every endpoint except the token exchange**. The version
rides in the `User-Agent`, not a header of its own.

Symptom: every call starts failing at once, while `yazio login` still works.
Fix: set `YAZIO_USER_AGENT` to a current YAZIO app User-Agent.
Handled by: `src/client.mjs` maps it to `ApiChangedError` (exit 7) naming the User-Agent in use.

## 2. The refresh grant is documented but unproven

`grant_type=refresh_token` appears in the spec, but no reference implementation exercises it —
one upstream client carries a TODO asking whether refresh exists at all, and the community MCP
server sidesteps the question by re-running the password grant, which it can do because it holds
the password for the session. This CLI cannot: it stores only tokens, by design.

So a refresh failure has no silent recovery. `src/auth.mjs` reports `authentication_required`
(exit 3) with the exact re-login command. **This is the one auth behaviour that has to be
confirmed against the live API.**

## 3. Nutrients are per one base unit, not per 100

A product's `nutrients` map is per **one** gram or millilitre — olive oil reads `8.84` kcal/g.
Energy is kcal; every other nutrient is grams. Getting this wrong is a factor-of-100 error in
someone's food diary, which is the highest-consequence bug available in this project, so the
conversion lives in one place (`src/normalize.mjs`) and is tested at the boundary.

Micronutrients in grams are ~1e-4 and round to a flat zero, which reads as "contains none"
rather than "too small to show" — hence `round()` in `src/util.mjs` falling back to three
significant digits.

## 4. Writes can be accepted and do nothing

- `daytime` outside `breakfast|lunch|dinner|snack` is accepted without complaint, and the entry
  is then filed where the user will never find it. Validate client-side.
- `DELETE /v22/user/consumed-items` answers `204` whether or not it removed anything: a wrong
  bucket is a silent no-op, and an `?id=` query parameter is accepted, answers 204, and does
  nothing at all. The bucket must be discovered by reading the day first, and the absence
  confirmed by reading it again.
- Writes and deletes both answer `204` with an empty body, so there is nothing in the response
  to verify against.

## 5. There is no server-side idempotency — but the client supplies the key

A consumed item's `id` is generated by the **client** as an uppercase UUID. That is a genuine
idempotency key: deriving it deterministically from an operation key means a repeated call
cannot silently create a second entry, and an uncertain write can be resolved by looking for
that exact id in the day rather than by sending the request again.

## 6. Two date formats that are not interchangeable

Reads address a day as `YYYY-MM-DD`. A written entry carries a full local timestamp
`YYYY-MM-DD HH:MM:SS` — space-separated, not ISO-`T`. Mixing them is accepted and puts the entry
on the wrong day.

## 7. Search will not run without a region

`sex` and `countries` are mandatory on `/v22/products/search`; blank answers
`400 "This value should not be blank"`. Both come from the authenticated profile, with the
country taken from `food_database_country` before `country` — YAZIO keeps those separate because
someone living abroad may still want their home database. Ranking is driven by the
`Accept-Language` header and hinted by the `locales` query parameter (underscore form,
`nl_NL,en_NL`).

Search results carry **no `eans`**, so confirming a barcode match requires fetching
`/v22/products/{id}`, whose body in turn carries no `id` of its own.

## 8. Terms of service

The API is private and unofficial. Using it is subject to YAZIO's terms, it is unsupported, and
it may stop working without notice.
